# 版本管理与变更约定（一期）

## 1. 版本号

本仓库建议使用 SemVer（`MAJOR.MINOR.PATCH`），并以 Git Tag 发布（例如 `v0.1.0`）。

- `MAJOR`：存在破坏性变更（向后不兼容）
- `MINOR`：新增能力，向后兼容
- `PATCH`：修复/补充文档或不影响兼容性的调整

一期建议从 `v0.1.0` 起步。

## 2. Thrift IDL 演进规则

### 2.1 允许的向后兼容变更

- 新增字段：必须使用新的 field id，且默认 `optional`
- 新增枚举值：追加枚举值（不重排、不复用旧值）
- 新增方法：追加服务方法（不修改已有方法签名）
- 扩展注释与文档：不改变语义

### 2.2 视为破坏性变更（需要升主版本）

- 删除字段或复用已有 field id
- 将字段从 `optional` 改为 `required`
- 修改字段类型或语义（例如 `string` → `i64`）
- 删除/重命名服务方法或调整入参/出参结构导致不兼容

## 3. 外部 HTTP API 演进规则

- canonical API 使用 `/api/v1/*`，如需破坏性变更应发布 `/api/v2/*`。
- `/pay`、`/verify` 属于兼容短链接入口，映射关系允许扩展，但不应改变既有语义。

## 4. 事件契约演进规则

一期事件使用 JSON payload，至少一次投递语义，消费者幂等去重。

- 允许新增字段（消费者忽略未知字段）
- 不允许移除/重命名核心字段（`event_id`、`event_type`、`tx_id` 等）
- 如需重大调整，建议引入 `event_version` 或发布新 `event_type`

## 5. 变更流程（建议）

- 提交 PR 时必须同步更新：
  - 相关 `docs/*.md`
  - 相关 `idl/*.thrift` / `openapi/*.yaml` / `examples/*`
- 对破坏性变更必须提供迁移说明（在 PR 描述或 `docs/*` 中）
