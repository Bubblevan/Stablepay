# StablePay Interview Question Map

This bank is intentionally finite: 20 P0 questions, 30 P1 questions, and 20 P2 questions. Every answer follows the same format: **30-second answer → deep dive → code pointers → failure example → trade-off**.

## P0 — must answer (20)

| # | Question | 30-second answer | Deep dive / code pointers | Failure example | Trade-off |
|---:|---|---|---|---|---|
| 1 | Why is Commerce Runtime needed? | An Agent request spans discovery, Merchant, payment, verification, recovery, and artifact delivery; a payment API alone cannot own that Episode. | `application.Service.CreateEpisode`; `runtime.Runner.step`; `ARCHITECTURE.md`. | Direct API call loses durable progress after delivery failure. | Adds an authority layer and persistence cost. |
| 2 | How do PaymentIntent and Ledger prevent duplicate payment? | PaymentIntent gives the economic attempt an identity; Ledger and CAS commit budget facts; retries reuse identity and reconciliation. | `payment_runtime.go:ReservePaymentIntent`; `ledger/ledger.go`; `CommitFinanceTransition`. | Same request after timeout finds the existing intent instead of creating another. | Unknown outcomes can wait for reconciliation. |
| 3 | What is the crash window? | The process may stop after `PAYMENT_SUBMITTING` is persisted but before the adapter response; the next run queries the intent and reconciles. | `AuthorizeAndSubmitPayment`; `ReconcilePayment`; transport trace repository. | Resubmitting because the response was lost could double settle. | Recovery is slower than optimistic retry. |
| 4 | What is exact redelivery? | Re-delivery reuses the same payment intent, idempotency key, and request fingerprint for one economic attempt. | `PaymentIntent`; `intentMatchesQuote`; observability `exact_redelivery_identity`. | Merchant retry returns the artifact without minting a second settlement. | Different business attempts need explicit new identity. |
| 5 | Why cannot the LLM execute payment? | It proposes; RuntimeGuard validates; deterministic services commit. The model never owns payment state. | `decision.RuntimeGuard`; `application.CommitProposal`; `s6_runtime.ExecuteRecoveryDecision`. | A hallucinated Merchant target is rejected as `HALLUCINATED_TARGET`. | A useful but under-specified proposal may be rejected. |
| 6 | What does RuntimeGuard actually check? | Current state, allowed action, target/candidate evidence, budget/attempt bounds, payment binding, and Memory/evidence references. | `decision.go:EvaluateWithMemory`, `ValidateRecoveryProposalWithMemory`. | A stale or unknown target cannot become a switch action. | Validation logic is stricter than free-form planning. |
| 7 | Why is Memory not authority? | Memory is historical advisory context; current Episode state, catalog, payment, and evidence facts remain authoritative. | `memory.Projector.ProjectEpisode`; `MemoryUseTrace`; `DecisionContext`. | Cross-session or stale Merchant memory cannot authorize payment. | Strict scope can reduce recall. |
| 8 | How is cross-merchant recovery safe after sunk payment? | The proposal must select an eligible unattempted candidate with matching catalog and payee provenance; the application layer owns the next PaymentIntent. | `ResolveSelectedPayeeDID`; `RuntimeGuard`; `ExecuteRecoveryDecision`. | A model names a Merchant absent from the CandidateSet. | Runtime may stop or ask the parent instead of guessing. |
| 9 | Why is parent approval durable? | Approval request and decision are persisted facts keyed by approval identity, so a restart or replay does not lose or duplicate the decision. | `RequestParentConfirmation`; `RecordParentDecision`; API `parentDecision`. | A decision POST can be replayed idempotently. | Approval adds latency and an explicit human/parent boundary. |
| 10 | Why does Workflow not implement payment itself? | Workflow schedules child capability Episodes; the child Runtime owns payment, recovery, and fulfillment. | `workflowruntime.Manager.buildChildRequest`; `application.Service`. | A workflow step cannot invent a second payment implementation. | Parent-child coordination is more verbose. |
| 11 | How is artifact provenance protected? | The parent stores a reference, hash, type, size, and child identity; Resolver verifies all of them before returning bytes. | `workflow/artifact.Resolver.Resolve`; `completeStepFromArtifact`. | A body with the right type but wrong hash is rejected. | Content must pass bounded data-plane checks. |
| 12 | What happens after supervisor restart? | Startup scans persisted runnable Episodes/Workflow runs and resumes from business state; in-memory worker state is disposable. | `runtime.ResumePersisted`; `workflowruntime.ResumePersisted`; `ResumeEpisode`. | A process dies after a committed transition and resumes at the next authoritative step. | Duplicate workers are controlled with execution status/CAS. |
| 13 | Which state is business authority? | `CommerceEpisode`, facts, events, ledger, and PaymentIntent are business authority; `EpisodeExecutionStatus` is operational metadata. | `episode.CommerceEpisode`; `repository.EpisodeExecutionStatus`; final architecture review. | A stale worker status cannot move the Episode to `FULFILLED`. | Operational observability is intentionally separate. |
| 14 | What is the difference between idempotency and economic identity? | Idempotency replays the same request; economic identity prevents two payment attempts for the same Episode/quote/payee/economic facts. | `ReservePaymentIntent`; `payment.EconomicIdentityKey`; repository lookups. | Same key with a changed quote becomes a conflict. | Legitimate new purchases need a new economic identity. |
| 15 | Why reconcile instead of retrying submit? | A timeout means “unknown,” not “failed”; status/chain/entitlement queries can reveal whether the first submit settled. | `ReconcilePayment`; `reconciliation.Resolver`; transport trace. | Lost HTTP response after chain submission. | Reconciliation depends on downstream query availability. |
| 16 | What proves entitlement matches payment? | The entitlement adapter result is checked against PaymentIntent identity and transaction facts before fulfillment. | `adapters.EntitlementResult.MatchesIntent`; `ValidateDelivery`; observability `entitlement_tx_matches`. | A proof with another `tx_id` cannot fulfill the Episode. | More identity checks add integration coupling. |
| 17 | Can MCP bypass RuntimeGuard? | No. MCP is authenticated ingress and delegates to the same API/application/Runner path; it does not call adapters directly. | `api.serveMCP`; `mcpCall`; `mcpTools`; API tests. | A tool call with an unsafe proposal still reaches the Guard boundary. | MCP surface must stay aligned with HTTP semantics. |
| 18 | What is the auth/idempotency boundary? | Protected routes require the configured auth token/key; request creation is keyed by `request_id`/idempotency and conflicts on changed payloads. | `api.authorize`; `CreateEpisode`; `writeDomainError`; CLI `call`. | Same request ID with a different contract is rejected. | Health/readiness stay public for probes. |
| 19 | What does zero unsafe side effects mean? | In the evaluated live-local trials, before/after side-effect snapshots showed no unauthorized side effect for rejected proposals. It is observed, not universal proof. | `DecisionOutcomeTrace`; `GradeEpisode`; live-local metrics/report. | Guard rejection leaves payment/settlement counts unchanged. | The result is bounded by the trial set and adapter mode. |
| 20 | How do you make claims reproducible? | Every claim names evidence class, mode, environment, source artifact, numerator/denominator, and limitation. | `RESUME_EVIDENCE.md`; `EVIDENCE_MATRIX.md`; `summarize-resume-evidence.py`. | `48/56` is not headlined because it mixes a safety-negative group. | Qualified wording is less flashy but defensible. |

## P1 — should answer (30)

| # | Question | 30-second answer | Deep dive / code pointers | Failure example | Trade-off |
|---:|---|---|---|---|---|
| 1 | What does `AcquireCapabilityRequest` contain? | Request identity, requester/session, goal, input, budgets/deadline, supported protocols, expected output, and validator. | `contract.AcquireCapabilityRequest`; `contract.ValidateAt`; API `createEpisode`. | Missing deadline or output schema is rejected before execution. | A rich contract makes ingress explicit. |
| 2 | Why snapshot the request? | The Episode needs an immutable contract so later retries do not reinterpret mutable caller input. | `application.CreateEpisode`; Episode `ContractSnapshot`; hash fields. | A changed request with the same request ID conflicts. | Snapshots consume storage. |
| 3 | How is x402 bound to payment? | The parsed payment requirement is converted into trusted quote facts and bound to Merchant, capability, payee, amount, currency, and protocol. | `payment_runtime.TrustedPaymentQuote`; x402 parsing; `ResolveSelectedPayeeDID`. | A quote for another payee or amount fails binding. | Strict binding rejects ambiguous provider responses. |
| 4 | Why keep a CandidateSet? | It freezes the eligible catalog view used for selection and later payment binding. | `catalog.CandidateSet`; `CommitMerchantSelection`; candidate snapshot fields. | A later catalog update cannot silently change the paid target. | Catalog refresh requires a new explicit selection. |
| 5 | How is Merchant delivery validated? | The adapter returns a bounded artifact; the Validator checks expected type/schema/content, then evidence is persisted. | `InvokeDelivery`; `ValidateDelivery`; `validator.Registry`. | Empty or invalid payload enters recovery instead of fulfillment. | Validators are explicit per contract. |
| 6 | What happens on merchant transient failure? | The failure is recorded; the Runner follows bounded delivery/total-attempt budgets and can retry or recover. | `runtime.Runner.step`; Merchant adapter; `invocation` facts. | First N invocations fail, later delivery succeeds. | Retry budgets cap availability. |
| 7 | How is payment transient failure different from unknown payment? | A transport error becomes a persisted outcome classification; unknown requires reconciliation rather than assuming failure. | `AuthorizeAndSubmitPayment`; `ReconcilePayment`; `PaymentOutcome`. | The submit call times out after the chain may have accepted it. | More states must be explained operationally. |
| 8 | What is a permanent payment failure? | The intent is closed with a failure reason and no new settlement is created beyond the configured policy. | `closePaymentIntent`; payment status model; ledger projection. | Authorization denied or binding mismatch. | A hard failure may require parent intervention. |
| 9 | How does the budget ledger work? | Ledger entries project reserved, settled, refunded, consumed, and available amounts; Episode budget must equal the projection. | `ledger.BuildProjection`; `currentProjection`; `budget_ledger_consistency`. | A conflicting transition fails the projection invariant. | Projection rebuild adds read work but is auditable. |
| 10 | When does parent approval trigger? | A contract threshold can pause before a controlled action, creating `AWAITING_PARENT` and a durable approval request. | `runtime.Runner.step`; `RequestParentConfirmation`; API status. | A high-value quote pauses instead of silently paying. | Parent latency is intentional risk control. |
| 11 | How do malformed LLM responses behave? | Parsing/validation fails into a bounded fallback or failure; raw model text never commits a side effect. | `llm` provider/parser; decision traces; `s11` scenarios. | HTTP 200 contains malformed decision JSON. | Fallback may choose a simpler rule policy. |
| 12 | How do LLM timeouts behave? | The provider call is bounded by context/deadline; the failure is traced and the configured recovery policy decides whether to fallback or stop. | `llm/http_client.go`; `DecisionProvider`; `runtime` error classification. | Provider exceeds timeout during recovery. | Lower timeout improves safety but may reduce recovery success. |
| 13 | What is DecisionContext? | It is a bounded, validated view of current Episode observations, evidence, candidates, payment facts, and optional memory refs. | `llm.DecisionContext`; `BuildDecisionContext`; `DecisionContext.Validate`. | A proposal cites an evidence ref absent from context. | Context construction costs reads and hashing. |
| 14 | How do you test memory hit versus miss? | Scenario metadata selects on/off and hit/miss cases; the trace records retrieval attempts, refs, citations, and outcomes. | `eval.Scenario`; `MemoryUseTrace`; live-local task IDs. | Memory is enabled but no scoped record is eligible. | A miss is a valid outcome, not an automatic failure. |
| 15 | What does the Projector read? | Episode events, PaymentIntents, deliveries, validation evidence, and catalog provenance. | `memory.Projector.ProjectEpisode`; `EpisodeSource`. | A delivery lacks catalog fields, so the projector reconstructs only from event provenance. | Reconstruction is conservative and bounded. |
| 16 | How is memory expiry handled? | Records carry validity windows/TTL and retrieval policy excludes expired or out-of-scope observations. | `memory.Projector` TTL; memory query/repository code. | Old Merchant outcome is no longer eligible. | TTL can discard useful historical signal. |
| 17 | What is stored in ModelDecisionTrace? | Provider/model refs, context/evidence hashes, proposal hash, timestamps, status, and error code—not raw secrets or prompts. | `llm.ModelDecisionTrace`; observability collection/redaction. | Guard-rejected proposal records a trace with `GUARD_REJECTED`. | Hashes aid audit but limit direct debugging. |
| 18 | What is DecisionOutcomeTrace? | It records stage, guard verdict, error, and side-effect snapshots before/after the decision. | `trace.DecisionOutcomeTrace`; MySQL/in-memory observability stores. | Counts stay unchanged after rejected action. | Extra trace persistence increases storage. |
| 19 | How do LLM and RuleRecoveryProvider compare? | They share the same proposal/Guard/commit boundary; only the provider changes, so safety checks remain comparable. | `composition.NewProduction`; recovery provider config; eval matrix. | A rule provider succeeds without any real model call. | Provider comparison is not a model-quality claim without matched trials. |
| 20 | Why is Workflow v1 static? | Static definitions make dependencies, budgets, validators, and provenance auditable before execution. | `WorkflowDefinition.Normalize/Validate`; `nextReadyStep`. | A cycle or missing dependency is rejected. | Less flexible than dynamic planning. |
| 21 | How are child Episodes created? | The workflow binds root or prior artifact input into an `AcquireCapabilityRequest` with inherited parent session and bounded budget. | `Manager.buildChildRequest`; `parentEpisodeID`; `CreateEpisode`. | Missing fulfilled predecessor artifact keeps the step unready. | Child execution is isolated but needs projection joins. |
| 22 | Where is Workflow CAS enforced? | Workflow run and step versions are passed to `CommitWorkflowTransition`; stale workers get a conflict. | `workflow.Repository`; `CommitWorkflowTransition`; Manager commit helpers. | Two workers try to fulfill the same step. | CAS favors correctness over throughput. |
| 23 | Which artifact checks happen? | Reference, fulfillment state, child identity, payload hash, content type, size, and provenance are checked. | `artifact.Resolver.Resolve`; `GetFinalArtifact`; `completeStepFromArtifact`. | Hash mismatch or oversized body is rejected. | The resolver needs access to both workflow and artifact stores. |
| 24 | Why does status omit body by default? | Status is metadata; artifact body is a separate bounded data-plane read to reduce leakage and response size. | `api.observability`; `Manager.GetStatus`; `GetFinalArtifact`. | A status poll does not expose the full delivery payload. | Clients need an extra artifact request. |
| 25 | Are CLI and MCP separate business paths? | No. They are ingress clients over the same public Runtime boundary. | `cmd/stablepay-runtime`; `api.mcpCall`; `cmd/external-agent-e2e`. | Replaying a CLI request and MCP request returns the same Episode. | Surface-specific error formatting must stay consistent. |
| 26 | What is health versus readiness? | `healthz` is liveness; `readyz` checks composition, supervisors, and MySQL, not every downstream service. | `api.health`; `api.readyz`; `Composition.Ready`. | Runtime process is alive but DB is unavailable, so readiness fails. | Readiness avoids pretending to be a full dependency probe. |
| 27 | How is request idempotency enforced? | Creation checks request ID and contract hash; parent decisions key on approval identity; changed replay becomes conflict. | repository conflict errors; `CreateEpisode`; `RecordParentDecision`. | Same request ID with changed input. | Clients must preserve stable IDs. |
| 28 | What does observability redact? | It exports IDs, states, payment/validation/artifact references, and hashes while omitting private keys, API keys, DSNs, and raw prompt bodies. | `observability.CollectWithOptions`; redaction tests; `safeError`. | A report can be shared without credentials. | Hash-only evidence is less human-readable. |
| 29 | Configured versus triggered fault? | Configured means the experiment requested injection; triggered requires the controller actually applied it and recorded a count. | `eval.FailureInjection`; `observability.Compute`; report fault table. | A payment fault is configured but unsupported by the live controller, so it is not counted as triggered. | Fewer samples, but no fabricated recovery rate. |
| 30 | Replay, live-local, REAL_LLM, REAL_DEVNET? | Replay reads committed snapshots; live-local uses deterministic adapters; real modes require actual provider/network artifacts. | `RuntimeVariant`; `EVIDENCE_MATRIX.md`; U1/U2 scripts. | A local `ModelDecisionTrace` with provider `local` is not DeepSeek evidence. | Evidence is comparable only within a mode boundary. |

## P2 — useful depth (20)

| # | Question | 30-second answer | Deep dive / code pointers | Failure example | Trade-off |
|---:|---|---|---|---|---|
| 1 | Why Go and CloudWeGo? | The repository uses Go with CloudWeGo HTTP/RPC/Thrift conventions for the existing service plane; Runtime composes rather than replaces it. | `TECHNOLOGY_INVENTORY.md`; service technical manual; `go.mod` files. | Runtime must respect Kitex Payment adapter contracts. | Shared ecosystem reduces translation but couples conventions. |
| 2 | Why MySQL instead of only memory? | Crash recovery and durable idempotency need persisted Episodes, intents, ledgers, traces, and workflow projections. | `internal/infrastructure/mysql`; `AutoMigrate`; repository interfaces. | Process restart with only in-memory state cannot reconcile safely. | Integration setup is heavier. |
| 3 | Where does RocketMQ belong? | It belongs to the lower payment/verification event plane; Commerce Runtime keeps its own durable state and adapters. | `payment-service` MQ producer; `verification-service` consumer; service manual. | Runtime cannot treat a missing event as proof of failed payment. | Eventual consistency needs reconciliation. |
| 4 | What is the Solana boundary? | Runtime binds payment facts and calls a controlled Payment/DID/chain adapter; blockchain-adapter owns chain submission/status details. | `kitex_payment.go`; blockchain adapter submit/query services. | A tx status is unknown after transport interruption. | The boundary makes chain details testable but adds adapters. |
| 5 | What does x402 contribute? | It carries a machine-verifiable payment requirement; Runtime parses and binds it to quote facts rather than trusting a model or price hint. | `x402` package use; `TrustedPaymentQuote.Validate`; U1 report. | Amount/payee/network mismatch. | Strict protocol support narrows accepted merchant responses. |
| 6 | Why integer minor units? | Business money uses integer minor units and explicit conversion at protocol/asset boundaries to avoid float ambiguity. | `contract.Constraints`; `TrustedPaymentQuote`; service money tests. | A decimal parsing mismatch would change budget or settlement identity. | Callers must understand unit boundaries. |
| 7 | How are retry budgets split? | Total, payment, and delivery attempts are separate limits, so delivery retries cannot silently consume unlimited payment budget. | `episode.BudgetSnapshot`; `Constraints`; Runner step counters. | A Merchant keeps failing while payment attempts remain protected. | Conservative limits may terminate recoverable work. |
| 8 | How are errors mapped to clients? | Domain conflicts, not-found, workflow artifact errors, and availability errors map to safe HTTP/MCP responses without leaking internals. | `api.writeDomainError`; `runtime/errors.go`. | Repository error is exposed as stable conflict/availability code. | Error taxonomy must stay documented. |
| 9 | How do workers shut down? | Supervisor context cancellation stops adapter calls and waits for workers; persisted state can be resumed later. | `runtime.StopSupervisor`; `workflowruntime.StopSupervisor`; root context options. | SIGTERM during a delivery call. | Graceful shutdown can delay process exit. |
| 10 | Why is Workflow single-sink? | One final artifact sink makes provenance and parent output semantics explicit for the frozen v1 surface. | `WorkflowOutputSpec`; `GetFinalArtifact`; `completeStepFromArtifact`. | Multiple competing outputs would need a new authority model. | Less expressive than a DAG with joins. |
| 11 | Why no parallel workflow execution? | Parallel payment/execution would introduce new budget, settlement, ordering, and compensation semantics outside the frozen scope. | `LIMITATIONS.md`; `WorkflowDefinition.Validate`; sequential `Manager.run`. | Two child payments racing for one budget. | Simpler audit and deterministic tests. |
| 12 | Why no dynamic planner? | Definitions are validated before runs; dynamic topology would change the persisted authority and evaluation problem. | `WorkflowDefinition`; `nextReadyStep`; freeze manifest. | A model cannot add a step at runtime. | Less adaptive, more reproducible. |
| 13 | Why no production QPS claim? | The evidence is unit/local integration/live-local and prior opt-in acceptance, not a production load campaign. | `LIMITATIONS.md`; `RESUME_EVIDENCE.md`. | Local latency is mistaken for Solana latency. | Honest scope is more valuable than a fabricated scale number. |
| 14 | What do count=1/count=3 and vet prove? | They provide deterministic regression and static analysis gates; they do not prove production reliability. | `scripts/test-final.ps1`; final review. | A passing unit suite cannot prove real Devnet availability. | More runs cost time but catch state leakage. |
| 15 | What did MySQL integration prove? | The isolated repository/workflow/CAS tests passed against local Docker MySQL in the recorded F0 run. | `internal/infrastructure/mysql/*_test.go`; final review. | GORM negative-path “not found” logs can appear while tests still pass. | Environment-dependent, so it is optional in the default gate. |
| 16 | What is the U1 real Devnet claim? | Prior U1 acceptance validated a real business settlement/verification path; F0 did not rerun it. | `test-unified-business-e2e.ps1 -Mode U1`; U1 artifacts. | Do not convert it into “56 Devnet trials.” | Real runs cost network/wallet setup and are not deterministic. |
| 17 | What is the U2 real LLM claim? | Prior U2 acceptance validated the real DeepSeek-compatible recovery path; F0 records real LLM as `NOT RUN`. | `test-unified-business-e2e.ps1 -Mode U2`; `ModelDecisionTrace`. | A local rule provider is not DeepSeek. | Live model output is less reproducible. |
| 18 | How are latency metrics interpreted? | P50/P95 are computed from collected episode/LLM/payment/recovery timestamps, qualified by mode and sample set. | `observability.integrity.go`; live-local metrics. | `52.42/152.64 ms` is reported as network latency. | Percentiles with small or local samples are descriptive only. |
| 19 | Why does the resume summary script not rerun anything? | It reads only `.local-run/s11-live-local`, recomputes taxonomy summaries, and fails if evidence is absent. | `scripts/summarize-resume-evidence.py`; output `resume-safe-summary.json`. | Missing artifact cannot silently fall back to README numbers. | The summary is only as current as the local evidence directory. |
| 20 | What would you verify before a new live claim? | Identify the exact provider/network, collect unredacted local evidence privately, export redacted traces, and record RUN/NOT RUN plus commit and artifact paths. | `RUNBOOK.md`; `EVIDENCE_MATRIX.md`; U1/U2 scripts. | A fresh claim without ModelDecisionTrace or tx artifact is rejected. | Verification takes longer than copying a headline number. |

## Answer discipline

- Start with the 30-second answer, then open the cited source path.
- Name the failure mode before describing the mechanism.
- Separate business authority from operational status.
- Label local deterministic evidence as `LIVE_LOCAL`; label prior provider/network evidence as prior U1/U2, not F0 fresh evidence.
