# StablePay 最终汇报讲稿草案

## 第1页 封面

大家好，我们是 StablePay AI 项目组。今天我汇报的主题是，我们如何围绕 AI Agent 的自主支付问题，设计并落地一套基于稳定币、DID 和 x402 协议的支付基础设施。我们的目标，不只是做一个能支付的 demo，而是去探索，当 Agent 开始替人执行真实任务、甚至替人买东西的时候，支付这一环到底应该怎样设计。

---

## 第2页 目录

我今天的汇报主要分成四部分。第一部分是项目背景和核心问题；第二部分是后端微服务和整体技术方案；第三部分是云端部署、Agent 客户端和最终成果；第四部分是我们的总结、反思和展望。

---

## 第3页 项目背景

这个项目的出发点，其实来自一个很具体的问题。今天绝大多数支付系统，默认服务对象都是“人”。它要求你先开户、做 KYC、绑卡、记密码，再去完成支付。但是 Agent 没有身份证，也不会像人一样点开银行 App 输入密码。它真正需要的，是一种自己能够持有、能够签名、能够被验证的身份，以及一种自己能够发起的支付动作。

所以我们项目想解决的核心问题就是，当 AI Agent 不再只是一个聊天机器人，而是开始代替人执行消费行为时，支付链路应该如何被重新设计。

---

## 第4页 从人类支付到 Agent 支付

如果从技术视角来看，传统支付链路本质上绑定的是“人类账户体系”，而 Agent 支付更像是“程序可执行的身份与授权体系”。所以我们没有沿着银行卡、密码、短信验证码这条路继续往下走，而是选择了本地钱包、DID 身份、签名授权和链上结算这一套机制。

这样做的好处是，Agent 不需要依赖人工输入敏感信息，而是可以通过本地密钥完成签名，通过后端完成验签和结算，再把支付结果反馈给业务系统。换句话说，我们是在把支付从“人机交互动作”，改造成“机器可验证协议”。

---

## 第5页 产品定位与切入场景

在产品定位上，我们希望做的不只是一个单点支付工具，而是一套面向 Agent 生态的支付底层逻辑。我们选择的第一个切入场景是 Skill 市场。原因很简单，很多 Skill 作者并不只是想开源，他们也希望自己的能力被合理定价、被真实购买。

所以我们把 StablePay 放在 Skill 交易场景里，去打通“未购买返回 402 challenge、客户端完成支付、支付后重试业务请求、商家完成交付”这一整条闭环。这个场景足够真实，也非常适合验证 Agent 支付到底能不能跑起来。

---

## 第6页 核心技术方案总览

围绕这个问题，我们搭建了三层体系。最下面是支付和身份基础设施，包括 DID、网关、支付、链上结算、验证和查询六个后端模块；中间是 Agent 客户端，也就是 OpenClaw 插件、MCP server 和 CLI 工具；最上层是实际接入场景，包括商家后端、文档站和云端部署体系。

这个设计的关键点在于，我们没有把所有逻辑塞进一个插件里，而是把“身份”“支付”“结算”“验单”“查询”这些能力拆开，让它既能服务单一宿主，也能逐步扩展到整个 Agent 生态。

---

## 第7页 后端微服务总览

后端部分我们一共拆成六个核心模块，分别是 API Gateway、DID Service、Payment Service、Blockchain Adapter、Verification Service 和 Query Service。

其中，API Gateway 负责统一接入和安全控制；DID Service 负责机器身份；Payment Service 负责支付状态机；Blockchain Adapter 负责和 Solana 链交互；Verification Service 负责购买关系确权和 X 验证；Query Service 负责余额、交易、收益和销售查询。

如果把它看成一条链路，就是外部请求先进入网关，再进入 Payment，Payment 同步调用 DID 和 Blockchain，支付成功后异步发事件给 Verification，最后商家和客户端再通过 Query 与 Verification 查询结果。

---

## 第8页 API Gateway

我负责的第一个核心模块是 API Gateway。这个模块不是简单的路由转发，而是整个系统的第一道安全边界。

它主要做了几件事。第一，统一外部入口，把请求按路径和方法转发到不同服务。第二，把鉴权拆成了两段：先抽取 header 信息，再调用 DID 服务做验签。第三，做防重放和限流。防重放的思路是，把 did、nonce、timestamp、path、method 组合成唯一指纹，落到 Redis 里，防止同一个签名跨接口重放。限流则同时从 IP、DID 和 route 三个维度做控制。

---

## 第9页 DID Service

DID Service 负责的是机器身份这一层。它会生成一对 Ed25519 密钥，把公钥编码成 `did:solana:<pubkey>` 这样的标识，并把状态持久化下来。

它对外最重要的能力，是签名校验。也就是说，当某个 Agent 发来支付请求时，后端不仅要知道“这个 DID 存在”，还要知道“这个请求确实是持有该私钥的一方签出来的”。同时，我们还加了时间戳窗口和 nonce 检查，避免旧请求被无限重放。

这里我们采用的是一个轻量化 DID 实现。它借用了 W3C DID 的命名和身份思想，但没有做成完整的 DID Document 解析器。这一点我们在答辩时会诚实说明。

---

## 第10页 Payment Service

我负责的第二个核心模块是 Payment Service，它可以理解成整个支付链路的中枢。因为它正好串起了 Gateway、DID、Blockchain 和 Verification。

Payment Service 首先接收标准化支付请求，然后做请求校验、幂等控制和状态流转。幂等是这里的关键，因为支付场景里最怕重复扣款。我们的做法是引入 `X-Idempotency-Key`，再结合请求体 hash 做校验。同一幂等键如果对应不同请求体，会直接拒绝；如果请求完全相同，则复用已有结果。

支付成功后，Payment 不会同步等待所有后处理逻辑完成，而是把支付事件发到 RocketMQ，再由 Verification 异步消费写入购买记录。这样主支付链路响应更快，系统也更容易扩展。这个设计本质上是用最终一致性换主链路的实时性。

---

## 第11页 Blockchain Adapter

Blockchain Adapter 负责把上层支付语义转换成真正的链上操作。我们当前聚焦的是 Solana 和 USDC。

这里比较有意思的一点是，我们支持两种模式。第一种是买家本地先签一个 partial-signed transaction，再由热钱包补 fee payer；第二种是纯托管模式，由服务端直接构建并签名转账。前一种更适合强调“Agent 自主支付”，后一种更适合平台托管场景。

为了方便排查链上问题，我们还加了一套统一审计日志，会在关键阶段打印 base64 交易、fee payer、签名数和转账账户信息。这样如果发生扣错账户或者签名异常，可以很快定位到底是在哪个阶段出的问题。

---

## 第12页 Verification Service

Verification Service 主要承担两个任务。第一个任务是消费 Payment 发来的 `payment_events`，把“哪个 Agent 买过哪个 Skill”这件事落成可查询的购买记录。第二个任务是做 X 验证和奖励发放，也就是用户 onboarding 过程里的身份确认。

为什么要把验证单独拆成一个服务？因为支付成功和购买关系落库，本质上是两种不同职责。Payment 只负责“钱有没有付出去”，Verification 负责“这笔钱是否对应到某个 Skill 的访问权”。拆开之后，商家侧就可以专注查购买关系，而不用直接理解支付细节。

---

## 第13页 Query Service

Query Service 负责的是查询层，包括余额、交易、收益和销售记录。这个服务的定位不是做核心支付，而是把后续面向用户和面向商家的信息都沉淀出来。

它一方面会读账本数据，另一方面也会去查链上余额，所以可以把“链上真实余额”和“系统内部交易记录”放在一起看。这样无论是用户看自己的消费，还是商家看自己的 sales 和 revenue，都会更直观。

---

## 第14页 云端部署总览

后端能力搭起来之后，我们没有停留在本地 demo，而是继续把它部署到了云上。整体链路可以概括成：本地开发完成后，构建镜像推送到 ACR，再由 ACK 集群拉起 Pod，通过 ALB Ingress 暴露到公网。

这部分的意义在于，它证明我们的项目不是停留在“代码能跑”的层面，而是已经考虑了真实服务部署、统一入口、服务编排和外部访问这些工程问题。

---

## 第15页 CI/CD 与运维亮点

在云端部署之外，我们还把重点放在了发布和运维的可持续性上。一个典型问题是，消息队列这类基础设施如果只靠手工维护，很容易在重启、迁移或者环境切换时出问题。

所以我们专门做了 topic 初始化 job，把关键 topic 的创建前移到部署流程里。同时在 K8s 层面支持滚动发布和回滚，让系统在出故障时能够快速止损。对我们来说，这一页想表达的不是“我们会写 YAML”，而是“我们有意识地把系统做成能运维、能复盘、能回滚的工程项目”。

## 第16页 Agentic Plugin

Agent 客户端这一层，是我们项目和普通后端支付系统最不一样的地方。因为我们的用户不是直接点网页按钮的人，而是可能通过 OpenClaw、Claude Code、Codex 这类宿主调用工具的 Agent。

所以我们把 StablePay 能力封装成了统一工具集。当前最成熟的形态是 OpenClaw 插件，同时我们也在同一套代码里实现了 MCP server 和 CLI 入口。也就是说，我们不是把支付逻辑硬写死在一个宿主里，而是在往“跨宿主、跨 Agent 生态复用”的方向演进。

## 第18页 工具矩阵

在工具层面，我们当前一共整理出了 18 个核心工具。这里不需要一个个背工具名，更适合按能力分组来讲。

第一类是身份和钱包相关能力，比如创建本地钱包、绑定已有钱包、注册 DID；第二类是支付相关能力，比如配置限额、构建支付策略、通过 gateway 发起支付；第三类是商家和验证相关能力，比如商品浏览、购买、X 验证状态查询和销售查询。

## 第19页 Onboarding 状态机

为了让没有 Web3 背景的用户也能用起来，我们专门设计了有状态的 onboarding 流程。它会按步骤检查本地配置、主密钥、后端连接、签名环境、钱包、DID、X 验证、奖励领取、支付限额和余额状态。

每一步开始之前，都会先运行 doctor 做只读诊断，确认没有 required error 才往下推进。这样做的目的，是避免用户在“还没创建钱包”或者“后端没连上”的状态下直接走到支付阶段，最后连错在哪里都不知道。

换句话说，这一页体现的是我们对真实用户体验的考虑，而不只是把功能堆出来。

---

## 第20页 Agent 支付端到端链路

这一页是整个项目最核心的一条主线。具体流程是这样的：商家后端先返回一个 402 challenge，Agent 客户端拿到挑战后，在本地完成签名与策略检查，然后把支付请求通过 Gateway 发给 Payment Service。Payment 再调用 DID 和 Blockchain 完成校验与结算，支付成功后异步通知 Verification，最后客户端重试业务请求，商家返回真正的 200 结果。

这条链路的价值在于，它把“业务授权”和“支付动作”解耦了。商家不需要自己处理钱包和链上逻辑，只需要按协议返回 challenge，并在业务侧检查购买关系就可以了。

---

## 第21页 插件层安全设计

AI Agent 自主调用支付工具，最大的风险不是接口报错，而是模型误判。比如模型看到工具“返回了一个对象”，就误以为支付已经成功，继续往下走，这其实是很危险的。

所以我们在插件层做了三层保护。第一，支付失败不会伪装成成功返回，而是显式返回 `failed`、`policy_denied` 或 `manual_confirmation_required`。第二，超过阈值的支付必须要有明确确认参数。第三，本地状态和密钥不是明文存储，而是用 AES-256-GCM 做加密。

也就是说，我们不是假设 LLM 一定可靠，而是在工具接口层主动约束它。

## 第23页 用户侧闭环

从用户视角看，完整流程是这样的。用户先安装插件并初始化，系统自动引导它创建本地钱包、注册 DID、完成验证和奖励领取，然后配置支付限额。之后用户在 Skill 市场里挑选商品，小额购买可以自动完成，大额购买则会触发二次确认。

---

## 第24页 开发者侧闭环

从开发者视角看，接入方式也被尽量简化了。商家只需要准备自己的钱包和 Skill DID，在业务接口里先做一次 verify 检查：如果没买过，就返回 402 challenge；如果买过，就正常返回 200 和业务结果。

除此之外，我们还配了 Mintlify 文档站，把接入指南、API reference 和测试说明整理出来。也就是说，我们不只是交付了一个后端服务，还尽量把它包装成一套别人可以看懂、可以接、可以调试的开发者体验。
